# Rev 系コマンド

GitHub PR のコードレビュー支援ツール

## 基本フロー

`/rev <PR URL>` → `/rev-post` → `/rev-check <PR URL>`

## 前提条件

以下を確認する。満たさない場合は作業を止めてユーザーに確認する。

- GitHub MCP の認証が有効
- 作業ツリーに未コミットの変更がない
- ローカルの HEAD がレビューに適した状態になっている（PR 情報の取得後に確認する）
  - 未マージ PR: HEAD が PR の head commit と一致している
  - マージ済み PR: HEAD が PR の merge commit を含んでいる（HEAD と head commit の差分を把握した上でレビューする）

## 制約

- **GitHub 操作は GitHub MCP を使う**（`gh` コマンドは使わない）
- **コード修正は行わない**
- **PR の承認（Approve）は行わない**

## レビュー方針

**時間がかかっても良いので、品質の高いレビューを行う。** とくに **「深さ」を重視** し、**最低でも数件は指摘を出すつもり** で深く掘り下げる(時間より「深さ」「最低 N 件」を意識する方が、浅い『問題なし』で止まらず取りこぼしを拾える)。

重視する観点は以下の 4 点：

1. **保守性・既存コードとの一貫性**
   - プロジェクトの既存パターンとの一貫性を既定とする
   - 同様の機能を持つ既存ファイルを参照し、スタイル・命名・設計の踏襲を確認する
   - ただし既存パターンが唯一の正解ではなく、別のやり方（ベストプラクティスや好み）に寄せるメリットが移行コストに対して大きい場合は、そちらへ移行する
2. **バグがないか**
3. **セキュリティに問題がないか**
4. **パフォーマンスに問題がないか**

### テンプレ追従(tsync)PR の場合

個別 PR 差分だけを見ると取りこぼし(部分適用の残差・古い版の移植・生成物の不整合)を見逃す。案件リポジトリと**テンプレ現行ツリー全体の差分**を取り、案件固有・既指摘・別途対応(deferred)を除いた**意図しない乖離**を探す。`-` 行(テンプレが持ち案件が欠く)が取りこぼしの典型。`<defaultBranch>` は追従先テンプレのブランチ(通常 `main`、variant 由来案件はその variant ブランチ)。

```sh
# 共有で差分があるファイル(= 取りこぼし候補)
git diff template/<defaultBranch> --diff-filter=M --stat -- . ':(exclude)apps/web/app' ':(exclude)migrations' ':(exclude)infrastructures' ':(exclude).env*' ':(exclude)**/gen/**'
# テンプレに在って案件で消えたファイル(怪しい削除)
git diff template/<defaultBranch> --diff-filter=D --stat
# ../line-miniapp-template をチェックアウトしているなら: diff -r <案件dir> ../line-miniapp-template
```

不審な差分は `git log` / 該当 PR を辿って経緯を確認する。生成 `.d.ts` は `tsc --skipLibCheck false` で隠れた型エラーも拾う。

## 優先度基準

| 優先度 | 内容                                                       |
| ------ | ---------------------------------------------------------- |
| High   | 実行時エラー、セキュリティ、データ破損、機能不動作         |
| Medium | 規約違反、パターン不整合、パフォーマンス、ドキュメント不足 |
| Low    | コード整理、未使用コード、命名改善、リファクタリング       |

## 指摘の構成要素

指摘ごとに以下を含める：

- 優先度、タイトル、対象箇所、問題点と理由、修正案（コード）
- 既存パターン（スタイル・設計指摘のみ）

行コメントとして投稿する際も上記の構成は同じで、以下のみ取り扱いが変わる：

- 対象箇所はアンカー（path/line）で表現されるため本文には含めない
- 修正案が対象行の置換で表現できる場合は suggestion 記法を使う（置換範囲とアンカー行範囲を一致させる）
