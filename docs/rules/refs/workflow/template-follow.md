# テンプレート追従と follow ラベル

## 目的

テンプレリポジトリ `entermotion-jp/line-miniapp-template` の更新を、各派生案件リポジトリが取りこぼしなく追従するための仕組み。
「気づきづらい / 取り込み漏れ / 追従度が担当者の匙加減 / 差が広がるとコンフリクト」を防ぐ。

## 仕組み(2層)

1. **follow ラベル**(テンプレ repo 側): テンプレ PR に「下流案件がどの程度取り込むべきか」を示すラベルを付ける。
2. **`tsync` スキル**(派生案件 repo 側): `.template-sync.json` で同期状態を管理し、未取り込みの更新を候補提示・選択取り込みする。
   ラベルがあれば優先度に使い、無ければ本ドキュメントの基準で Claude が分類する。

## follow ラベル(3段階)

| ラベル | 意味 | 下流の扱い |
| --- | --- | --- |
| `follow:must` | 全案件が取り込むべき | 必須 |
| `follow:recommended` | 基本取り込み推奨 | 推奨 |
| `follow:optional` | 任意(多くは見送り) | 任意 |

## follow:coordinate(取り込みタイミング修飾・上の3段階と直交)

`follow:must/recommended/optional`(重要度=どれだけ取り込むべきか)とは**別軸**の修飾ラベル。重要度ラベルと**併用**する(置き換えない)。

| ラベル | 意味 | 下流の扱い |
| --- | --- | --- |
| `follow:coordinate` | **いずれ取り込むべきだが、単独取り込みは危険**。前提/ペア/インフラ/タイミングを調整してから入れる | `tsync` 既定で **deferred(保留)**。調整が済んでから取り込む |

- **必ず重要度ラベルと併用**する(例: `follow:must` + `follow:coordinate`)。原則 `must`/`recommended` と組む(`optional` の「多くは見送り」とは意味が衝突するので通常組まない)。
- **PR 本文に調整情報を必須**で書く: ①なぜ単独取り込みが危険か ②何を待つ/何とペアか(前提 PR・データ移行・お客様同意・バージョン整合) ③どこで誰と調整するか。ラベルは「既定を deferred に倒し本文を読ませる」役で、具体は本文が持つ。

## 判定基準(ルーブリック)

**人が当てずっぽうで選ばない。Claude が差分・内容を見て本基準で判定し、人が確認する。**
変更の「対象領域(共通基盤か案件固有か)」と「種類」で決める。

### `follow:must`

- バグ修正(動作不良・クラッシュ・データ不整合)
- セキュリティ修正
- これを入れないと CI / ビルドが通らない、または共通基盤が壊れる互換性対応
- 全案件の品質・一貫性を担保する共通の仕組み/基盤(これが入らないと案件間で品質・運用がばらつく)

### `follow:recommended`

- 共通基盤の改善・リファクタ・命名/型の強化
  (`apps/api` 共通処理、共通コンポーネント、`config` 系、`tsconfig`、lint、`docker`、`Makefile`、CI など)
- 依存更新(セキュリティ以外の `deps`)。**インフラ結合のもの(DB エンジン・CDK・ランタイム等)も基本ここ(recommended)。タイミング/検証調整が要るものだけ `follow:coordinate` を併記**
- `docs/rules/` などルール・ドキュメントの更新

### `follow:optional`

- デモ / サンプル画面・サンプル機能
- 案件ごとに異なる前提の強い変更(具体的な画面文言・レイアウト・ビジネスロジック)
- 特定案件向けの実験的変更

### `follow:coordinate`(重要度ラベルへ追加で付ける修飾)

「取り込むべきだが**単独/即時の取り込みが危険**」なときに、重要度ラベルへ**併記**する。典型:

- **インフラ結合・破壊的変更**: 既存リソースの置換/再作成・データ移行を伴う(例: RDS の `storageEncrypted` 化 → 既存 RDS の再作成)。
- **前提/ペア依存**: 別 PR や外部設定が前提(例: SES 送信ドメイン検証が前提、DMARC 強化と送信基盤がペアの PR)。
- **インフラ結合のバージョン更新でタイミング/検証調整が要るもの**(例: CDK / Node ランタイム更新で Lambda 等の更新が走る)。※ AWS 影響ゼロな bump(例: MySQL のマイナー更新)は casual に入れてよく coordinate 不要。
- **お客様同意・運用調整が要るもの**。

> coordinate は「いずれ入れるべき」が前提。**入れなくてよい**ものには付けず重要度だけで判断する(`optional` 等)。インフラ結合バージョンアップは基本 `recommended`(従来 `optional` 扱いだったが「多くは見送り」では取りこぼす)。**タイミング/検証調整が要るものだけ `follow:coordinate` を併記**(例: CDK ランタイム更新)。AWS 影響ゼロな bump(例: MySQL)は coordinate 不要。

### tie-break(迷ったとき)

1. 「入れないと**壊れる/危険**か?」→ Yes なら `follow:must`
2. 「共通の改善で**入れた方が良い**か?」→ Yes なら `follow:recommended`
3. 「その案件**特有で多くは不要**か?」→ Yes なら `follow:optional`
4. 性質が混在する PR は**高い方**(must > recommended > optional)に寄せる。
5. それでも不明なら `follow:recommended` を既定とし、人が最終判断する。

> 注意: ファイルパスだけで機械的に決めない。案件固有領域(画面など)でも、**内部リファクタ・型強化・共通化**は方針を揃えたいことが多く `follow:recommended` になりうる。逆に共通領域でも案件依存の強い実験は `follow:optional`。**変更の中身**を見ること。

## PR 作成時の自動ラベル付与

**テンプレリポジトリ本体(`origin` が `entermotion-jp/line-miniapp-template`)で PR を作成するときは、follow ラベルを自動で付与する。**
派生案件リポジトリ(`origin` が別 repo)では付与しない。判断は `git remote get-url origin` で行う。

「PR を作って」と依頼されたときの手順:

1. PR の差分(変更ファイルと内容)を確認する。
2. 上記ルーブリックに沿って `follow:must` / `follow:recommended` / `follow:optional` を 1 つ判定する。**さらに単独取り込みが危険なら(上記 `follow:coordinate` の典型に該当)、`follow:coordinate` を併記**する。
3. PR を作成し、判定したラベルを付与する(GitHub MCP で PR 作成 + ラベル付与。`gh` は使わない)。
4. どのラベルをなぜ付けたかを 1〜2 行で報告する。性質が混在して判断に迷うときのみ、付与前に確認を取る。

> `follow:coordinate` は著者が見落とすことがある(例: RDS 再作成のような気付きにくい破壊的変更)。**インフラレビュアは気付いた時点で後付け**してよい(その際 PR 本文に調整情報を追記する)。

前提: follow ラベル(`must` / `recommended` / `optional` / `coordinate`)がテンプレ repo に作成済みであること(未作成だと付与に失敗する)。

## tsync との関係

- `tsync` は取り込み候補の優先度付けに follow ラベルを使う。
- `follow:coordinate` が付いた PR は、`tsync` が**既定で deferred(保留)**にする(単独取り込み危険・要調整)。重要度ラベルは並び順に使う。
- ラベルが無い PR は、`tsync` が**本ルーブリックで**分類する(fallback)。
- したがってラベルは「精度を上げる上乗せ」であり、無くても `tsync` は動く。ラベルがある方が判定は正確。

## やってはいけないこと

- ラベルをパスだけで機械的に決める(中身を見ずに判定しない)
- 性質が混在する PR を安易に低い方へ寄せる(取り込み漏れの原因)
- follow ラベルと `tsync` のルーブリックで**別の基準**を持つ(本ドキュメントを唯一の基準とする)
- 単独取り込みが危険な PR に `follow:coordinate` を付けず、`must` / `recommended` だけで流す(下流が気軽に取り込んで事故る)
